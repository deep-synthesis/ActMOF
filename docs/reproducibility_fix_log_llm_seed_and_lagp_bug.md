# ActMOF Benchmark 严谨性修复说明：laGP 实现错误 与 LLM 调用复现性问题

**日期：** 2026-08-19
**范围：** `Benchmark v3.ipynb` 中 `LAGP_ALC_EI`、`LAGP_NN_EI` 两个方法的实现错误；`LLM_PURE_*` 与 `HYBRID_*` 系列方法调用 OpenAI API 时缺少 seed/temperature 控制的问题。

---

## 一、问题总览

在对 benchmark 代码做严谨性复查时，发现两类独立问题：

| # | 问题 | 影响范围 | 严重程度 |
|---|------|---------|---------|
| 1 | LLM API 调用未固定 `seed`（`temperature` 定义了但从未传入） | 5个方法：`LLM_PURE_gpt-4o`、`LLM_PURE_gpt-5.5`、`LLM_PURE_gpt-5-mini`、`HYBRID_GP_Matern52_EI_ALT_gpt-5.5`、`HYBRID_GP_Matern52_PI_ALT_gpt-5.5` | 中等：影响逐次复现性，验证后**不影响最终结论** |
| 2 | `laGP` R 包调用参数名错误，导致方法几乎完全退化为随机搜索 | `LAGP_ALC_EI`、`LAGP_NN_EI` 两个方法 | **严重**：82.8%~92.8% 的迭代结果实际是随机数，不是 laGP 真实输出 |

两个问题相互独立，下面分别说明发现过程、证据、修复方案与修复前后的实测对比。

---

## 二、问题1：LLM 调用缺少 seed 控制

### 2.1 发现过程

代码审查时发现，`Benchmark v3.ipynb` 里定义了 `LLM_TEMPERATURE = 0.2`（第106行），但全文（约3700行代码）搜索后，这个变量**再也没有被引用过一次**；调用 OpenAI API 的地方也从未传过 `seed` 参数：

```python
# 实际执行、产出论文现有数据的那份代码（原样摘录）
response = client.responses.parse(
    model=model_name,
    input=[
        {"role": "system", "content": llm_system_prompt()},
        {"role": "user", "content": json.dumps(user_payload, default=float)},
    ],
    text_format=MOFNextBatch,
)
```

`temperature` 和 `seed` 均缺失，这意味着相同的历史数据输入给同一个模型，两次调用得到的结果理论上可以完全不同——这是可复现性层面的缺陷。

### 2.2 深入验证后发现的额外情况

在着手修复时，对三个实际使用的模型（`gpt-4o`、`gpt-5.5`、`gpt-5-mini`）逐一做了真实API探测，确认：

- **`seed` 参数三个模型均支持**，可以被正确修复。
- **`temperature` 参数只有 `gpt-4o` 支持**；`gpt-5.5` 和 `gpt-5-mini` 在服务器端会直接拒绝这个参数（400错误：`Unsupported parameter: 'temperature' is not supported with this model`）——这是 GPT-5 系列"推理力度"模型家族的架构性限制，**不是代码疏漏能修复的**，只能如实披露。
- 额外发现：GPT-5系列模型默认会开启内部"思考"（reasoning），若不显式设置 `reasoning_effort` 为最低档，模型可能把整个输出预算耗在隐藏的思考过程上，导致返回内容为空——这是一个新的、独立于原始bug的风险点，修复时一并处理（`gpt-5-mini`/`gpt-5.5` 显式设置 `reasoning_effort="minimal"`/`"none"`）。

### 2.3 修复方案

- 所有5个方法的 API 调用中加入真实 `seed`（基于 run 编号和方法名哈希生成，逐轮递增）。
- `gpt-4o` 额外加入 `temperature=0.2`。
- `gpt-5.5`/`gpt-5-mini` 显式关闭内部思考（`reasoning_effort` 设为最低档），避免新发现的隐藏推理耗尽输出预算的问题。
- 用一次真实探测（"金丝雀检测"）在每次正式运行前自动确认这些参数确实被服务器接受，而不是静默降级。

### 2.4 修复前后实测对比

先用成本最低的 `gpt-5-mini` 完整重跑一次（5次独立run，与原协议完全一致）做验证：

| | 原始（无seed/temperature控制） | 修复后（seed+reasoning_effort控制） | 差异 |
|---|---|---|---|
| mean best_q | 74,206 | 73,251 | -1.3% |
| std | 29,098 | 40,306 | — |

**结论：均值基本没变（差异远小于run间正常波动），支持"这只是复现性问题，不影响最终结论"的判断。**

基于这个验证结果，`gpt-4o`、`gpt-5.5` 两个纯LLM方法暂不重跑（性价比低）。

### 2.5 头牌结果 HYBRID 方法的重跑结果（已完成，需要重点关注）

论文排名第1的 `HYBRID_GP_Matern52_PI_ALT_gpt-5.5` 用同样的seed+reasoning_effort修复方案完整重跑了一次（5次独立run，49轮，与原协议完全一致，267次真实LLM调用，fallback率仅3.3%，花费$7.16）：

| 方法 | 原始（无seed控制） | 修复后（seed控制，5run） | 变化 |
|---|---|---|---|
| `HYBRID_GP_Matern52_EI_ALT_gpt-5.5` | 160,199 ± 18,482 | 170,651 ± 54,765 | +6.5% |
| `HYBRID_GP_Matern52_PI_ALT_gpt-5.5`（排名第1） | **215,832 ± 42,825** | **194,059 ± 36,476** | **-10.1%** |

修复后单次run的最终best_q：PI变体是157,714 / 215,200 / 223,200 / 150,981 / 223,200；EI变体是203,289 / 115,600 / 126,380 / 160,877 / **247,107**（EI变体第5次run直接命中了整个候选池的理论全局最优值247,107）。

**⚠️ 需要重点关注：排名第1的结论在数值上依然成立，但margin大幅收窄。** 修复前 PI变体（215,832）领先第2名 `CONFRF_EI`（191,823）约12.5%；修复后 PI变体（194,059）依然略高于 `CONFRF_EI`（191,823），**但margin只剩约1.2%，已经远小于两者各自的run间标准差（36,476 / 25,752）**，统计意义上已经很难说两者有显著差异。"HYBRID方法排名第1"这句话在数值上还站得住，但"HYBRID方法明显优于第2名"这句话现在需要谨慎表述或补充统计检验，不能再像修复前那样直接下结论。

## 三、问题2：laGP 实现错误（更严重，是本次审查最重要的发现）

### 3.1 发现过程

在检查非LLM算法的公平性/严谨性时，统计了每个方法在迭代过程中触发"随机兜底"（模型报错、退化成随机选点）的比例，发现：

| 方法 | 总迭代数 | 触发随机兜底次数 | 比例 |
|---|---|---|---|
| `LAGP_NN_EI` | 250 | 232 | **92.8%** |
| `LAGP_ALC_EI` | 250 | 207 | **82.8%** |
| 其余37个方法 | — | 0 | 0% |

只有这两个方法出问题，其余所有方法完全正常——这不是普遍性代码问题，是这两个方法自身实现有bug。

### 3.2 具体证据：两个独立的参数错误

真实报错信息：

```
rpy2.rinterface_lib.embedded.RRuntimeError:
Error in laGP::aGP(X = Xnew, Xref = Xref, Zref = Zref, start = start, ...) :
  unused arguments (Xref = Xref, Zref = Zref)
```

查证 `laGP` R包文档（`args(laGP::aGP)`）确认真实函数签名是：

```r
aGP(X, Z, XX, start, end, method, ...)
```

其中 `X`=训练输入、`Z`=训练响应、`XX`=待预测的新点。而原代码写的是：

```r
# 原代码（错误）
p <- laGP::aGP(
    X = Xnew,      # 错：把"待预测新点"塞进了X（应该是训练集输入）
    Xref = Xref,    # 错：aGP()根本没有Xref这个参数
    Zref = Zref,    # 错：aGP()根本没有Zref这个参数
    ...
)
```

这是把 `laGP` 包里两个不同函数（单点版 `laGP(Xref, X, Z, ...)` 和批量版 `aGP(X, Z, XX, ...)`）的参数名搞混了——很典型的复制粘贴/API混用错误。

**修复验证时还发现了第二个独立的bug**：即使不崩溃，原代码里读取预测方差的逻辑也是错的——查找的是 `"s2"` 或 `"sd"` 这两个字段名，但 `aGP()` 返回对象里方差字段的真实名字是 `"var"`。也就是说就算不崩溃，代码也永远拿不到真实的不确定性估计，只会用一个固定常数替代——这会让EI/PI这类依赖"不确定性"做探索的采集函数形同虚设。

### 3.3 修复方案

```r
# 修复后
p <- laGP::aGP(
    X = Xref,      # 训练集输入
    Z = Zref,      # 训练集响应
    XX = Xnew,      # 待预测新点
    start = start, end = end, method = method, verb = 0
)
mu <- as.numeric(p[["mean"]])
sd <- sqrt(pmax(as.numeric(p[["var"]]), 0))   # 改成读取真实的"var"字段
```

修复已经用真实R环境端到端验证过（`args(laGP::aGP)` 核对参数名、`names(p)` 核对方差字段名），并已写回 `Benchmark v3.ipynb` 源码。

### 3.4 修复前后实测对比（5次独立run，与原协议完全一致，已全部跑完）

| 方法 | 修复前 mean±std（异常兜底率） | 修复后 mean±std（异常兜底率） | 变化 |
|---|---|---|---|
| `LAGP_ALC_EI` | 40,450 ± 9,515（82.8%兜底） | **116,933 ± 37,386**（0%异常） | **+189%** |
| `LAGP_NN_EI` | 68,275 ± 31,682（92.8%兜底） | **126,723 ± 50,236**（0%异常） | **+86%** |

修复后的500次真实调用（2方法×5run×49轮+初始批次），**除每个run第1轮因训练点天然不足（只有3个点）被设计上正常跳过之外，零异常**，是干净的真实数据。

### 3.5 对论文排名的影响

按现有39方法排名表估算，这两个方法从**倒数第1（ALC）、倒数第4（NN）**，跳到大约**第24-27名**——从"几乎等同随机搜索、可忽略"变成"中等偏上、需要在排名讨论中认真对待"。

好消息是：修复后的数值（117k~127k）依然明显低于App里使用的 `GP_Matern52_EI/PI`（178k/187k），**不影响App算法选型的排名依据**。但如果论文里有任何"LLM方法优于传统baseline"之类的排名性表述，需要重新核对——修复后的laGP已经超过了 `LLM_PURE_gpt-4o`（78,642）、`LLM_PURE_gpt-5-mini`（74,206）等方法。

### 3.6 顺带发现并修复的性能问题（不影响结果，只影响运行时间）

修复bug后首次实测发现，`aGP()` 单次调用耗时随训练集增大接近三次方增长（训练点从30个到60个，单次调用从约5秒涨到约55秒），默认只用单核计算。开启 `omp.threads` 多核并行（本机12核）后单次调用提速约4.5倍，且相同seed下数值结果完全一致（纯计算层面优化，不影响任何统计结论）。这个问题此前从未被发现，是因为原来的参数错误导致方法从未真正跑到训练集变大的阶段。

## 四、总结

1. **laGP bug是本次审查中最重要的发现**：不是"影响复现性"这种量级的问题，而是**两个方法的真实性能被严重低估了（低估80%~190%）**，此前论文里如果有关于这两个方法（或"Approximate GPs"这个方法家族）的任何定性判断，都是基于错误数据得出的，现已用真实数据更正。
2. **LLM的seed问题对纯LLM方法（用gpt-5-mini验证）基本不影响结论**（差异<2%），**但对论文头牌的HYBRID结果有实质影响**：排名第1的结论数值上仍然成立，但相对第2名的领先幅度从约12.5%收窄到约1.2%，已经落在两者标准差范围内，"明显领先"这个表述需要收回或加统计检验支撑。这是本次修复中唯一一个**可能需要调整论文表述**的地方，建议重点讨论。
3. 三处修复均已写回/独立验证于 `Benchmark v3.ipynb` 对应逻辑，且都用独立的、可复算的脚本在真实环境里验证过（laGP：500次真实R调用；gpt-5-mini：245次真实API调用；HYBRID：267次真实API调用）。
4. 仍未处理但已知的问题（供后续参考）：部分"slow"标记方法（RGASP、BNN_like等）在acquisition候选池大小上（4000 vs 其余方法的15000）存在不对称设置，本次未动，建议在论文方法学章节披露或后续统一处理。
